# 外壳与内核的接口版本（shell contract）

## 为什么

以前内核包只认「一个确切的 Portable 版本 + 一个确切的外壳指纹」。每发一次 Portable，launcher 文件就变，指纹就变，之前验证过的内核全部作废，旧版本用户也拿不到新内核——除非先更新 Portable。

现在内核包声明它**面向哪一版接口**（`requiredShellContract`，整数），外壳在自己的 `licenses/COMPONENTS.json` 里声明**自己说哪一版接口**（`shellContract`）。携带接口号的内核在号码相同时接受，不再比较 Portable 版本和指纹；需要较新默认插件的包会改用现有确切版本与指纹绑定，见下文。

## 接口指什么

外壳（`launcher/`）和内核运行时（装进 capsule 的 app 目录）互相点名的东西，共七类：

| 类别 | 内容 |
| --- | --- |
| `env` | 外壳传给内核的 `DSH_PORTABLE_*` 环境变量 |
| `bridge` | 页面与原生宿主之间的 `dsh-portable/*` 消息 |
| `cli` | 内核里的桥接服务调用的 `portable-cli` 命令 |
| `flag` | 这些命令用到的选项 |
| `file` | 内核按路径找的 `launcher/*.mjs` |
| `capsule` | 启动器能读的内核包文件格式，和打包脚本写出的格式 |
| `layout` | 外壳要求内核目录里必须存在的路径（方向相反：外壳提问，内核回答） |

冻结记录在 [`config/shell-contract.json`](../config/shell-contract.json)，由 [`scripts/shell-contract.mjs`](../scripts/shell-contract.mjs) 扫描生成。`tests/shell-contract.test.mjs` 每次都拿当前代码和记录比对，对不上就失败。

## 改了接口怎么办

```bash
node scripts/shell-contract.mjs check    # 看差异
node scripts/shell-contract.mjs update   # 兼容变化（外壳多提供了东西）：刷新记录，号码不变
node scripts/shell-contract.mjs bump     # 破坏性变化：号码 +1 并刷新记录
```

判断标准：

- 新版内核开始依赖一个旧外壳从没提供过的名字 → **必须 bump**。
- 外壳删掉了内核也在用的名字 → **必须 bump**（旧内核装在新外壳上会坏）。
- 内核不再处理外壳仍会发的消息 → **必须 bump**。
- 外壳多提供、或只改外壳自己用的名字 → `update` 即可。

工具只看得见名字。名字没变但行为变了（例如同一条消息换了字段含义），要手动 bump。

安全修复也可能使旧内核包不再可接受。0.9.4 将契约升至 2：旧契约 1 的胶囊使用修复前的 MCP 依赖，即使接口名字相同，也不能让切换内核重新引入它。可选内核必须用包含 MCP 2.3.0 覆盖的源码重新打包和验收；发布流程不能沿用契约 1 的目录记录，更新源仍须等新契约的内核验收通过才切换。

0.9.9 将契约升至 3，防止切换内核重新引入 Portable 应用层的配置恢复安全缺陷。旧契约 2 的胶囊包含修复前的插件配置恢复写回逻辑；它的签名仍可能有效，接口名字也可能相同，但不能再被修复后的外壳接受。恢复过程中在异步包管理操作后重新校验 profile 根和清单写入目标的保护属于这条安全边界，不能靠保留已安装的 Portable 版本号或指纹证明运行时代码仍已修复。

这次只提升安全语义版本，不重新定义 SDK 或接口名称，也不禁止旧版 DSH 引擎。需要继续使用旧 DSH 版本时，必须用包含当前 Portable 应用层修复的源码重新打包、验收并签发契约 3 的适配包；既有已签契约 2 的离线包和目录记录不能沿用。安装了契约 2 的旧外壳仍按既有规则接受契约 2 的包，契约 3 的包则要求先升级 Portable。

bump 的代价：旧号码的外壳不再收到新内核，会提示「先更新 DSH-Portable」。所以只在确实无法兼容时才用。

## 安装内核时发生什么

内核更新包是在某个较新的 Portable 上验证的，它自带的 `COMPONENTS.json` 写着那个版本和指纹。安装时**不能**把这些写进用户的安装目录：外壳文件没有变，产品更新检查、关于页都读这个文件。所以安装前会把外壳身份（Portable 版本、指纹、契约号、预装插件清单、Node、WebView2 信息等）合并回已安装的值，运行时部分（内核版本、pnpm、市场版本等）取自新包。预装插件清单属于外壳：压缩包放在启动器旁边的 `default-plugins/`，启动器还会逐项对照自己写死的哈希表，所以不能被新包改写。`adoptInstalledShellIdentity` 实现这一步，失败回滚时一并还原。

## 仍然单独检查的条件

接口号相同不等于全部兼容。发布端会固定同接口最早公开外壳的默认插件基线，读取锁定摘要验证过的真实包清单。目标内核不满足该基线的 peer 范围时，不再向所有同接口旧壳提供，而是绑定已验收的确切 Portable 版本与指纹；旧壳需要先更新 Portable。基线不随更新源前移，也不把元数据错误当作 peer 不匹配。

以下仍各自检查：随包 Node 版本、运行时布局（capsule/expanded）、更新机制自身的 `shellSchema`、更新器 schema。任何一项不满足会提示需要完整包更新。

## 没有接口号的旧版本

0.9.1 及更早的外壳不认识这个字段，仍按旧规则（确切版本 + 确切指纹）判断，所以这些用户需要先更新到带接口号的 Portable 一次，之后才能跟上新内核。这次更新后的提示也改成了「需要先更新 DSH-Portable」。

## 第三方插件

内核切换前，更新流程会用目标内核实际加载一遍现有 profile（`--dump-config`），加载不了就整个更新取消并回滚；能加载但插件声明的版本范围和新内核对不上，则更新完成后列出这些插件（`warnings`）。默认插件由 Updates 流水线按已验收外壳及固定接口基线核对。内核包不代替旧启动器升级其静态默认插件，用户自行更新的较高插件版本会保留；插件包和会话数据不会因兼容暂停而删除，可在官方插件页更新后重新启用。

## 改更新器代码前后的演练

动 `launcher/update-core.mjs`、更新器或接口版本号之前，先用 CI 里的 `windows-x64-build` 产物跑一次 `scripts/upgrade-drill.ps1`：它用真实的旧版本（默认最近三个稳定版）带着数据，经旧版自己的更新器升级到新构建，检查凭据、会话和插件是否保住。窗口全程隐藏，下载的旧包用完即删。改动后用同一份产物再跑一次，两次都必须全部 PASS。

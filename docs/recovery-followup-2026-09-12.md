# 更新中断恢复：第二轮收尾

## 确认并修复的问题

1. capsule 回滚先无条件删除当前清单与数据文件。如果断电发生在写入 prepared
   日志后、旧文件移入备份前，会删掉仍然有效的原文件。现在逐项检查备份和原文件，
   只替换有备份的文件；两者都缺失则停止并保留日志。已恢复的文件可以跨重试保留。
2. 独立修复通过 runtime-entry 进入时，原先会先加载 capsule。缺失或损坏的清单
   会在事务回滚前终止。现在 repair 检查到更新日志时，先调用仅依赖随包 launcher
   模块的 recover-update，再加载恢复后的运行时。复用产品锁、环境存活检查和原有
   回滚服务，不增加另一套文件恢复实现。
3. 恢复日志的操作 ID 原先允许 `.` 与 `..`。现在明确拒绝这两个值与非字符串 ID，
   拒绝时保持日志和数据不变，防止事务清理越出单次更新目录。

范围：显式修复入口可以处理这些中断；不声称任意损坏、备份丢失或 Node 自身损坏
都能自动修好。普通启动没有增加额外进程；没有待恢复日志的 repair 也不会启动预恢复子进程。

## 验证

- 完整源码 618 通过、0 失败、0 跳过。
- 回归覆盖备份前、清单单独备份、两个文件已备份、新文件安装后、恢复一半再次
  中断；核对原文件、许可证元数据和数据哨兵；再次恢复返回 none。
- 实际入口回归使用最小打包 fixture，损坏当前 manifest，从 runtime-entry 的
  repair 进入，确认先回滚再完成诊断。fixture 修正过缺失 pnpm 入口的问题。
- 本机隔离包的 DSH-Recovery.exe 在 prepared、manifest-backed-up、runtime-backed-up、
  testing 四个阶段均成功修复；testing 场景使用损坏的新清单与 capsule。
  每次都比较恢复前后原文件字节、COMPONENTS 元数据和工作区哨兵。
- 实际恢复 EXE 面对活跃且归属正确的产品锁拒绝恢复；运行时和日志不变。
  最初用测试运行器 PID 作为锁持有者不符合 Portable 进程身份，不能当作锁验证；
  最终使用隔离包内 Node、匹配 CLI 路径的独立进程签名完成验证。
- 恢复后 Win11 原生窗口进入工作区，交接 3,352 ms，加载层和工作区均捕获，
  8 个边缘/角落命中通过。没有用户桌面输入操作。

本次延用上一轮隔离底包，覆盖更新后的 launcher 模块和对应 shell fingerprint。
这仍是本地集成验收；正式发布前需要精确提交的跨平台成品矩阵。

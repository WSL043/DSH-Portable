# 同类产品对照与本轮取舍

核对日期：2026-09-12。以下为各项目公开文档与本仓库代码对照，不是安装体验排名或跨产品性能实测。
目标是找出 Portable 的真实缺口；不复制另一款聊天工作台，也不把上游 Agent 能力包装成我们独有的功能。

## Portable 应突出什么

1. **整个个人环境可携带**：默认会话、设置、插件与工作区集中保存；同系统同架构完全退出后可以搬走。外部目录、模型服务和系统权限仍需单独准备。
2. **产品与内核独立更新**：用户可以选通过当前资格验证的内核；发现、构建与验证自动化，失败不绕过验收直接上架。
3. **工作区打不开也能诊断**：独立恢复入口不要求 WebView2 或 DSH 后端先运行；本轮补齐了运行时损坏时先恢复更新事务的顺序。
4. **按需要选择离线体积**：Windows 标准包使用系统 WebView2，完整离线包携带运行时备用；模型权重与可用的本地模型服务另行准备。

这几项是当前产品能力的组合，不宣称其他产品都没有。官网本轮不改；竞品审查报告留在开发文档，不放进 Release 用户说明。

## 已落地的性能与结构整理

完整诊断原先分别为内核完整性和 profile resolver 各遍历一次依赖图。
现在通过 `inspectDshRuntimeState()` 在**一次只读诊断内**共享结果；删除两条重复扫描入口，resolver 检查留作内部实现。
每次新诊断和修复后的复查都重新读取清单，没有全局缓存、磁盘缓存或跨修复复用。

本机真实成品运行时含 482 个依赖包。前后版本交替顺序各测 8 次，比较完整诊断对象完全一致：

| 指标 | 原实现 | 本轮实现 |
| --- | ---: | ---: |
| 完整只读诊断中位耗时 | 314.44 ms | 193.38 ms |
| 降幅 | — | 38.50% |

这是文件缓存已热时的诊断耗时；不是首次启动、模型推理或端到端修复的加速百分比。
上一轮 resolver 文件检查并发优化已包含在两边基线内，两项百分比不能直接相加。
原始记录：`build/maintenance-acceptance/diagnostic-benchmark.json`；脚本同目录 `diagnostic-benchmark.mjs`。

源码回归沿用原有测试并扩展“健康 → 依赖损坏 → 恢复”流程，确认新诊断不会复用旧的成功或失败结果，会话原文保持不变。
本机源码测试：618 通过、0 失败、0 跳过。隔离 Windows 成品覆盖本轮启动器代码后，实际 `DSH-Recovery.exe` 验收 6 项通过：基础文件检查、实体目录故障诊断、不启动工作区导出报告、修复实体目录、重复修复无动作且数据保留、缺少 Node 时独立报错。日志为 `build/diagnostic-native-recovery.log`，详细结果为 `build/maintenance-acceptance/recovery-results.json`。
这是正式包基底上的本地集成验证；全量重新构建与跨平台成品以对应提交的 CI 为准。

## 后续按证据推进

| 优先级 | 项目 | 完成条件 |
| --- | --- | --- |
| 高 | 插件安全模式 | 先查上游是否有不改持久配置的禁用入口；验证后端与前端故障插件、默认插件、退出后恢复原配置、异常中断后可恢复。未满足前不把现有修复称为安全模式。 |
| 高 | 更新与迁移中断恢复 | 更新恢复已有故障注入验收；数据导入目前能处理捕获的异常，仍需单独验证进程被强制终止后的恢复，不把二者等同。 |
| 中 | Windows 签名 | 本仓库 [签名策略](../CODE_SIGNING.md) 仍记录申请中；只有取得资格、接入受控构建并验证真实成品签名后才修改宣传。 |
| 中 | 首次准备耗时 | 当前大头为运行时文件首次落盘。继续以文件数、字节数、准备阶段和工作区就绪测量；只在证明依赖边界后精简，不延迟加载未知依赖。 |

不为追赶功能数量新增手机远程、PPT 模式或重写 Agent 引擎。本轮保持现有产品范围，把共同规则收回共享服务并保留成品验证。

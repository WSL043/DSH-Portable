## 1. 产品方向

**把 DSH 变成可携带、可更新、可恢复的个人工作环境。**

核心用户是希望免配环境开始工作、换设备保留环境，以及提前准备后在断网下使用本地模型的人。
选择 Portable 的理由应直接体现在使用流程里：解压能启动、界面能管理、退出能搬走、出错能自救。
不以功能数量、测试数量、仓库 Star 或截图效果作为质量结论。

维护边界：

| 部分 | Portable 负责 | 不扩展成什么 |
| --- | --- | --- |
| 桌面与启动 | 窗口、快捷键、启动状态、进程退出、平台集成 | 官方聊天界面的长期分叉 |
| 官方内核 | 发现、构建、资格验证、版本选择、故障归因 | 每个官方缺陷的补丁发行商 |
| 插件市场 | 集成兼容、安装事务、默认体验、必要上游修复 | 第二个独立插件生态与功能竞争项目 |
| 默认插件 | 图片查看与会话管理的完整体验、数据兼容、独立发布 | 无限制接管第三方插件维护 |
| 用户数据 | 迁移、备份、恢复、凭据边界、路径重定位 | 自动猜测并重写未知上游数据格式 |

官方增加重叠能力时，先检查完整性与数据兼容，再移除对应补充实现；不因名称相同就停用整个插件。

## 2. 架构收敛方式

保留现有原生壳、Node 启动器、官方运行时和独立更新库，不整体重写。
先沿已有模块建立边界，只有同一规则出现多处实现或改动跨越过多职责时才拆分。
文件大只是审查信号，不以行数指标驱动重构。

依赖方向：原生壳和 CLI → Portable 服务 → 官方能力适配与文件系统。
原生 UI 只处理显示和输入；版本判定、修复计划、安装事务不各平台重复实现。
独立恢复入口复用服务层，不要求工作区、插件市场或官方后端先启动成功。

| 服务边界 | 现有入口 | 下一步审查重点 |
| --- | --- | --- |
| 生命周期 | launcher/portable-core.mjs、portable-cli.mjs | 启动状态与退出责任是否唯一，UI 是否自行推断就绪 |
| 更新 | launcher/update-core.mjs | 发现、可选资格、安装事务、恢复是否有清晰结果类型 |
| 修复与迁移 | launcher/repair-core.mjs、data-transfer.mjs | 用户数据与生成物分类是否共用，是否会误删或重复修复 |
| 内核准备 | launcher/runtime-capsule.mjs | 缓存命中、原子准备、失败清理、并发所有权 |
| 默认插件 | launcher/default-plugins.mjs、各插件仓库 | 随包版本、离线依赖、用户自行安装版本的所有权 |

需要统一的最小契约：操作 ID、阶段、结果码、是否需重启、可执行下一步、证据位置。
先映射已有日志和返回结构，补缺项，不再并行新增一套“更高级”的框架。
兼容适配优先检查公开能力；必要的版本分支必须注明触发证据、覆盖范围、退出条件。

退出条件：精确提交的源码验证、受影响平台成品检查、发布矩阵通过；失败日志不覆盖。
本批不引入新的数据格式、兼容协议或大型设置功能。

### P1：环境迁移与恢复，作为下一阶段的产品重点

以“旧环境 → 新目录 → 验证可用 → 切换”为统一流程，改善现有迁移能力而非另造导入器。
先生成预览：发现哪些会话、设置、插件、工作区引用；哪些是外部路径；哪些凭据不能直接跨机器使用。
目标已有内容时必须有明确冲突规则，不隐式覆盖；未知格式跳过并报告。

区分三种操作：

1. 整个目录移动：同系统同架构为首要支持范围，修正 Portable 所有的路径。
2. 数据导入：先备份/暂存和检查，成功后提交；支持中断恢复，来源保持不变。
3. 会话抢救：从用户授权提供的副本只读提取，展示可恢复、部分恢复、未知项；不承诺缺失内容无损恢复。

插件 ZIP 是安装来源，不是已安装插件本体。删除 ZIP 不视为卸载；卸载应通过明确入口更新配置和依赖。
可提供“导入本地插件包”，先展示包身份、兼容要求与依赖是否齐备，不把所有 ZIP 当作可信完整离线包。

验收：带中文和空格路径、目标冲突、取消、中断、磁盘空间不足、来源不完整、重复导入，以及重启后会话可读。
会话 ID/数量与设置语义比对优于只比较目录存在；敏感内容不进入公共日志。

### P1：更新机制降低维护成本

继续独立管理产品、内核、默认插件的版本。稳定/候选是通道策略，不能和产品/内核两条更新线混为一谈。
保持自动发现 → 当前产品资格验证 → 发布目录 → 用户安装；新上游版本不自动触发 Portable 发版。
已实现的历史回填继续保留，旧成功只作为重验资格，不作为新产品的兼容证明。

先衡量 CI 资格验证耗时、失败原因、历史回填积压与下载依赖故障，再优化构建复用。
近期 Node 编译头文件下载超时可以审查本机匹配 SDK/校验缓存；不以整条流水线反复重试掩盖原因。
普通上游变更进入差异报告，只有可执行的维护工作才形成 issue。

长期可研究独立兼容契约，但必须列明 Node、运行时布局、桥接能力、数据格式、默认插件宿主要求。
先以影子判定与现有严格检查对照，证明允许组合的正确性；再考虑复用产物。
没有稳定契约证据前继续精确绑定，不简单移除 Portable 版本或 fingerprint 检查。
通道目录的原子性、撤销已知坏版本、校验失败和安装中断必须纳入更新事务验收。

### P2：离线与性能，按证据投入

Windows 保留轻量启动器、标准 ZIP、完整离线 ZIP 三种清晰入口。
完整包优先使用系统 WebView2，仅缺失时准备随包运行时；固定运行时更新必须有维护记录。
macOS/Linux 按各自图形运行库说明前置条件，不套用 Windows WebView2 的包名与保证。
离线定义拆开写：程序启动、默认插件可用、本地模型推理、外部工具依赖；不把局部网络夹具等同整机断网。

先建设离线预检结果，告诉用户缺的是模型、服务、运行库还是插件依赖；不捆绑大模型增加所有人的包体积。
严格断网验收使用隔离环境覆盖浏览器、Node、模型服务和子进程，并保留真实工具调用证据。

性能分别测首次准备、缓存复用启动、目录移动后启动、更新后启动。
记录各阶段耗时、文件数、写入字节、缓存命中和内存峰值；相同环境比较中位数和慢样本，避免只报最快一次。
先移除重复扫描和重复校验，再考虑打包改造。只有确认不在启动依赖链上的资源可延后准备。
延迟加载必须有明确就绪状态与首次使用行为；不能把启动等待转移成用户首次点击卡顿。
涉及上游加载器的大改只有稳定收益明显超过兼容成本才采纳；无可靠收益的实验及时撤回。

### P2：默认插件与桌面细节

图片查看器围绕完整图片流程维护：图集、原图、缩放/拖动、高清标注、键盘、焦点恢复和下载。
会话管理围绕可靠数据操作维护：检索、归档、导出、恢复、删除确认、当前会话写入协调。
分别记录正式内核与候选内核的真实能力覆盖；版本号提升不代替实际操作验证。
用户已升级或卸载默认插件时不能在下次启动擅自覆盖或重新装回。

桌面交互统一点击开菜单、外部点击关闭、Esc、焦点和快捷键规则；加载态只保留一个状态来源。
缩放比例、主题切换与窗口边框作为固定视觉验收场景，不再凭局部截图反复堆样式。

## 4. 测试与维护工作流

测试的大网放在共享服务不变量：

- 更新成功只替换受管组件；失败回到已知状态；用户数据不受损。
- 修复只触碰确定可再生的对象；重复执行幂等；生成物缺失可恢复。
- 通道与兼容资格不混用；自动更新不降级；显式选择仍过资格检查。
- 启停、迁移、更新各自只有一个操作所有者，取消和中断有明确结果。

再用小量平台成品测试覆盖真正分流：Windows 窗口命中、macOS 生命周期、Linux 动态库等。
同一历史 bug 若已被共享不变量覆盖，可合并重复测试；特殊平台回归不能以“大网”名义删除。
按风险选测试，统计关键流程覆盖、逃逸缺陷与维护成本，不追求测试数不断上涨。

每项任务使用同一闭环：问题/证据 → 边界与最小方案 → 修改 → 定向验证 → 必要成品验收 → commit。
同一批代码先完成本地修改与定向验收，再集中推送一次。用户追加的独立改动另记提交与证据，不能引用上一提交的绿色 CI 作为新改动的验收结论。
每批只选一项主要改造及直接依赖；发现的无关问题进入待办，阻止审查无限扩张。
测试失败先保留现场并定位，不循环改测试直到变绿。
验收结果包含停止与清理阶段，退出码和结构化结果必须一致；性能采样排除测试驱动进程，保留原始值、峰值和可比基线。局部修复只补做受影响的验收，不无理由重跑已完成的长流程。
默认 main 上积累已验证提交；确需隔离时才短期分支，合并后删除。
发布从精确验收产物生成，文案只写用户行为变化；内部维护报告留在开发文档。

文档事实来自同一份发布元数据：版本、包类型、大小、内核、默认插件锁和验证范围。
截图附语言/主题/版本信息；截图更新必须实际拍摄与检查，不通过改文件名假装新版。
日志保留完整因果链并有界轮转；支持报告先脱敏，再汇总，用户预览后主动分享。

## 5. 排期与停手条件

第一批交付 P0，不预先承诺版本号。第二批集中做迁移恢复；第三批根据测量结果选择构建复用或首次启动优化。
默认插件功能更新单独安排，不与每次 Portable 发版强绑定。文档一致性随发布维护，官网暂不重开。

暂不做：新聊天工作台、多平台统一壳重写、任意旧内核永久支持、任意插件自动兼容、无来源镜像竞速、复杂遥测平台。
若重构无法指出解决的重复规则、具体故障或可测收益，就不进入实施。
若新的兼容层长期需要逐版本例外，停止扩展，重新审查上游接口与支持范围。

交付后的判断标准是：同类问题是否更少、故障是否更容易说明和恢复、更新是否无需人工追版本、用户是否更容易带走环境。

## 2026-09-27：后台预算、退出取消与故障释放

后台运行时清理现在按 1 秒/100000 条目预算检查候选，最终方案不预扫描整棵目录计算体积，避免大目录永远耗尽预算而无法回收。删除仍验证当前版本、租约、锁及路径，后台未统计的回收体积记为未知。手动 CLI 清理保留精确统计，目录使用迭代读取，每批最多 32 个文件大小查询，不套用后台默认预算。宿主退出取消后续工作；已经提交给操作系统的文件操作不能强制在 1 秒内中止。

| 内容 | 当前规则 | 仍需注意 |
| --- | --- | --- |
| DSH 解包后的运行时 | 后端启动 60 秒后清理不用的旧版本；当前版本和活跃租约保留 | 清理失败时保留目标并记录原因；不能保证磁盘被其他程序锁住时仍能回收 |
| 中断解包的临时目录 | 本轮补齐：只处理符合受管命名、创建超过 24 小时且原进程已退出的目录 | 新近创建、活跃进程、未知名称和目录链接保留；清理同时避让解包锁 |
| 启动历史 | 自动按 30 次、14 天、32 MiB 的规则淘汰历史记录 | 当前启动与无法安全识别的内容保留；限制不包含用户主动导出的支持报告 |
| 运行健康日志 | 有轮转，历史分文件也有限额；启动源码缓存在加载结束后释放 | 这些规则不等于已经完成连续数天的内存稳定性测试 |
| WebView2 浏览器数据 | 按 Portable 身份、位置和环境复用本机目录，由浏览器管理页面缓存 | 移动位置可能留下旧目录；混有登录状态和站点存储，目前不能直接删除整个目录作为缓存优化 |
| 随包 WebView2 的解包缓存 | 与 DSH 内核缓存分开 | 尚无覆盖其原生进程生命周期的自动旧版本清理，不能套用 Node 租约假设直接删除 |
| pnpm 插件存储 | 位于 Portable 的 `data/pnpm-store`，供依赖重用 | 更新插件可能增加旧内容；不能清空仍被插件链接或离线恢复需要的依赖 |
| 更新事务临时文件 | 成功提交后清理，未完成事务保留恢复材料 | 数据导入、插件修复的备份另有用途，不按普通缓存自动删 |
| 会话、图片附件、工作区、用户导出和备份 | 属于用户数据或主动保存的恢复材料 | 会随使用增长；保留并提供用户可理解的管理方式，不能为体积指标自动删除 |

## 本轮修复

原先清理器只识别完整的 64 位哈希目录。进程被强制结束时，解包阶段的
`.hash.pid.timestamp` 目录无法运行 `finally`，后续清理也会忽略它。
现在在现有后台清理流程中回收满足条件的中断目录，没有新加常驻清理进程或启动前全盘扫描。

清理旧运行时还会同时取得垃圾回收锁与解包锁，避免删除另一进程正在准备提交的版本。
使用租约仍在锁内复查。一个目标失败不会阻止其他目标；结果只统计实际成功删除的内容。

有删除或失败时，启动日志增加 `runtime-cache / maintenance-complete`，包含删除数量、中断目录数量、回收字节和失败代码。
顶层清理错误记录 `maintenance-failed`；没有清理动作时不刷日志。

验证使用独立临时目录，覆盖当前运行时、活跃租约、正在解包、已退出进程的陈旧残留、新近残留、未知目录、指向用户数据的链接及重复清理。
源码测试：619 通过、0 失败、0 跳过。记录：`build/long-term-cache-full-tests.log`。
缓存清理提交 `0424632` 的 [35 项成品 CI](https://github.com/WSL043/DSH-Portable/actions/runs/34681493341) 已通过，包括 Windows 2022/2025 原生启动与完整离线包。后续缓存报告与退出检查的修改另有[实机记录](long-term-acceptance-2026-09-12.md)，不能沿用该提交的 CI 结论。

缓存状态查询现在也统计受管的中断解包目录，查询本身不删除租约。
某个目录无法读取时返回 `complete: false` 和错误代码，其他目录仍提供可用统计；合计仅代表成功读取的部分。
损坏且无法确定所有者的租约按占用保留；由程序生成的 UUID 文件名仍能确认已退出进程时，才允许清理中断写入的租约。
文件大小查询限定为每批 32 个，目录逐个遍历，不随目录深度扩大并发。

## 2026-09-22：统一启动器日志保留与存储诊断

Windows 原生窗口已有 1 MiB 日志轮转，但 Node 入口（命令行启动、运行时准备、插件恢复）直接追加同一个 launcher.log。仅使用这些入口时，没有原生窗口替它限制增长。本轮统一 Node 写入函数，超过 1 MiB 时保留一代 previous；单条最多 16 KiB，异常和文件占用不阻断启动或恢复。历史超大文件首次轮转仍保留，下一次轮转才替换，避免修复时直接丢失全部旧证据。这不是严格跨进程磁盘配额，原生与 Node 并发写入仍属尽力诊断。

存储报告新增 skippedLinks、errors、limited，区分主动避开链接、读取失败和扫描预算不足。2026-09-22 对当前安装只读测量：pnpm-store 的普通文件逻辑大小 1,982,598,512 字节、1131 个文件，跳过 5 个链接，无读取错误、未超时。日志约 4.4 MiB。未删除用户依赖、备份或缓存，不能把逻辑大小当作回收收益。

验证：32 项针对性测试全部通过（日志轮转、异常目标保护、插件失败恢复、启动失败清理、存储报告及桥接接口）。Windows/macOS/Linux 打包脚本均复制 launcher/*.mjs，新模块属于现有打包规则。尚未进行新成品原生验收或发布。

### 依赖存储整理的下一步验收门槛

1. 以实际安装的 pnpm 版本和布局为准。官方最新文档的 v11/global virtual store GC 说明不能直接当作旧版本行为证据。
2. 建立当前所有 profile、待提交操作、回滚目标、明确保留的离线依赖的引用集合；未知引用保留。未解决统一插件操作锁之前，不接入自动清理。
3. 对相同插件反复启停和安装应复用内容；对持续升级的新版本，单独核算历史依赖增长，不能用重复安装同版本的测试代替。
4. 在隔离复制中进行整理；随后断网验收启动、插件加载、依赖重建及回滚。缺任一证据，不开放用户的一键依赖清理。
5. 设置页分别展示网页缓存、旧运行时、插件依赖、恢复材料，清理结果只汇报实际完成量。不能承诺会话附件或用户备份自动变小。

参考：[pnpm store 官方文档](https://pnpm.io/cli/store)。其 prune 后按需重新下载的前提不适用于 Portable 的完全断网恢复，因此不直接照搬自动 prune。


### 2026-09-22：复制安装的离线修复反例

- hardlink：整理后两个版本均断网重建成功；5 文件、12474 字节未减少。这证明这一组引用被保留，不代表收益。
- copy：整理命令成功，但两个版本断网重建均失败；5 文件降为 1 文件。这是阻止上线自动整理的反例，不能把命令退出成功当作产品验收通过。

## 2026-09-27：超量日志清理与扫描公平性

修复插件操作日志超过 2000 个目录后每次发现均整批退出的问题。达到扫描上限时保守地处理已经排序的子集，并将四分之一时间预算留给删除；子集中保留的最新记录不会导致删除全局最新记录，未知文件、近期日志、目录链接和争用中的官方 profile 锁继续受保护。超预算仍明确报告 limited，不宣称一次完成全部回收。

隔离目录 `build/log-retention-scale-oHoHSL/result.json`：2100 条过期日志加一条最新日志，以默认 2000 条扫描上限执行两轮，分别移除 1999 与 101，最新日志一直存在，第三轮无变更。这是合成文件系统验收，不是用户目录清理。6 项日志/存储定向测试通过。

存储占用查询改为四个有界串行扫描器并行，平分总条目预算，共用时间截止。插件存储过大时，备份、恢复材料和日志仍有扫描机会；总并发不随目录深度增长。超限类别仍显示部分结果，不把逻辑字节数称为可回收空间。这些源码改动尚未随正式版交付。

### 同日真实宿主调度修复

源码覆盖的 0.7.5 新目录验收发现：启动器直接启动 `portable-host.mjs`，原本放在 `runtime-entry.mjs` 的 host 分支没有经过，插件日志与旧运行时的后台清理实际都未调度。将两项合并到真实宿主调用的 `host-maintenance.mjs`，保留 60 秒延迟与 6 小时间隔，加防重入和退出取消；旧入口死代码移除。

实机后端两次启动分别在约 61 秒和 60 秒回收 1625、475 条过期合成日志。第二次同时回收一个合成闲置运行时目录，保留当前目录和带活跃进程租约的合成目录。后端均通过控制接口优雅退出。证据 `build/native-maintenance-product/maintenance-second-evidence.jsonl`；不是用户安装上的清理，也不代表 WebView2 或 pnpm store 回收已完成。

### 复制安装的引用保留实验

另一个必须保留的输入是 profile 内 `.dsh-portable-archives/sha512-<digest>.tgz`：CLI 将远程 tarball 下载到此处并写为 `file:` 依赖。迁移包没有排除此目录，因此不能将所有 profile 下的压缩包视作可再生下载缓存。

补充固定门槛 G3（2026-09-27）：`qualify-store-maintenance.mjs referenced-copy` 在整理后保持本地 registry 关闭，再执行十轮新版/回滚版离线安装，每次实际加载模块并核对版本。证据 `build/store-maintenance-referenced-copy-aY7z5T/result.json`：20 次安装均成功，每轮 store 均为 5 文件、12474 字节。它证明合成引用集合下重复操作不继续增长，不代表生产引用发现、锁或清理入口已经交付。

生产实现必须区分各环境自己的 `data/pnpm-store`，收集全部 profile 以及 `before-import-*` 中的 generated 依赖、启动修复旁备；`profiles/node_modules` 是生成的宿主解析入口，不能当作全部插件引用。导出的 `.dshdata` 会排除 node_modules 和 pnpm-lock.yaml，可加密且可保存在任意位置，因此不能宣称扫描当前目录就覆盖所有历史导出包的离线恢复需求。无法确定引用或存在未完成事务时应保留并说明原因。官方 profile 写锁与产品变更锁并非同一把锁，不能只持产品锁就开始 prune。

`qualify-store-maintenance.mjs referenced-copy` 在隔离 store 内为当前版和回滚版建立真实硬链接引用，再整理并断网以复制模式重建两个版本，均成功；无引用第三版本被回收（7 文件到 5 文件）。证据 `build/store-maintenance-referenced-copy-j5McVG/result.json`。对照重跑仍确认：普通 copy 整理后两个版本都不能断网重建，hardlink 对照可以。因此它只是可行性实验，不能直接接入用户清理按钮；生产实现仍需完整收集所有 profile/恢复引用、持锁、空间检查和失败恢复。

当时的 Windows 官方插件页成品脚本新增真实重启后延迟维护断言：过期日志必须删除、近期日志必须保留，不能仅直接调用清理函数。该阶段源码全仓 873 项：859 通过、14 条件跳过、0 失败。后续 `2cb9a17` 的成品 CI `36288060199` 已完成 39 项；它覆盖该批后台维护，不替代后来新增清理入口的验收。

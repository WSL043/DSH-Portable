# Windows 2022 启动验收判定修正

源运行：[34683129267](https://github.com/WSL043/DSH-Portable/actions/runs/34683129267)，产品源码 `4907561`，Windows 2022 原生任务失败。原始证据保存在 `build/ci-4907561/`。

失败产物的最后一次 DOM 采样已经出现工作区文字、加载层已消失；原生跟踪也记录了 `interactive-ready`（从宿主记录的 process-start 基准约 73.1 秒）。但最后采样附带的普通日志还停在 `dom-probe:True`。因此“从未交接到工作区”的原错误描述不符合已收集证据。

原脚本要求在统一截止时间前，既读到普通日志中的交接标志，又完成后续连续采样。临界时刻的日志可见性和稳定性观察会争用启动预算；此外浏览器 `performance.now()` 在导航后归零，不能作为整个启动过程的统一时钟。旧产物没有记录脚本的绝对截止时间，不能据此倒推原运行是否严格满足 75 秒预算，也不能直接改判通过。

修正采用同一 PID 的启动历史内 `interactive-ready` 绝对时间，必须仍在原启动预算内；最多额外观察两秒，用于确认八次连续的非空、无加载层且有主控件的工作区样本。超过预算的原生就绪仍失败。输出 `handoff-result.json`，区分缺少原生交接、启动超时和交接后不稳定；`cleanup-result.json` 记录停止结果，退出失败不再吞掉。

旧源码正则断言被替换为新判定入口的接线检查；独立行为测试覆盖临界前就绪、临界后就绪、错误 PID、观察期间加载层重现、空白或主控件消失。没有删除原生加载截图、交接来源和边缘命中检查。

该机器还存在真实的首次解包耗时：目录准备约 37.6 秒，文件写入阶段约 22 秒。这是单次托管 runner 的观测，尚未证明由 Defender、磁盘或当前改动导致；本补丁不宣称改善这些耗时，也不提高启动预算。

本机复验复用隔离产品目录，通过后台/CDP 运行，无前台输入。跨 Windows runner 的结论须以修正脚本运行同一成品的后续任务为准；此处修正的是验收与诊断，不是重新发布产品。

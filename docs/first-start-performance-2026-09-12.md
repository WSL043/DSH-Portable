# 首次启动体验与冷解包测量

用户第一次启动能否顺利进入工作区，是产品验收的一部分。不能用持续转圈或延长测试超时替代真实改进。

## 本轮交付

Windows 原生加载界面显示目录准备、运行文件展开和完成准备的实际阶段；前两个阶段分别使用已完成数量计算百分比，不伪装成整个启动过程的预计剩余时间。运行时日志与原生界面使用同一组进度数据，约每 500 ms 最多报告一次，并保证阶段完成事件。动画仍使用原来的原生加载环，没有新增覆盖层、倒计时或独立常驻服务。

运行时复用时不生成虚假的解包进度。先验证完整性，再开始写入；提交缓存成功后才进入插件和会话加载，原有中断恢复与占用保护保持有效。

## 本机比较结果

同一胶囊约 8,440 个文件、113 MB 内容，每次使用新建缓存目录，三轮交替执行，试验目录执行完即清理。操作系统文件缓存与实时扫描缓存未清空，因此不是全新系统或慢速磁盘的证明。

| 方案 | 原实现中位数 | 对比中位数 | 决定 |
| --- | ---: | ---: | --- |
| 共享父目录、建目录与写文件交错 | 2,990 ms | 3,045 ms | 没有收益，不合入 |
| 同步文件接口 | 2,951 ms | 3,012 ms | 没有收益，不合入 |
| Node 文件线程池 4 → 16 | 3,024 ms | 2,874 ms | 本机约 5% 改善，暂不修改产品默认值，继续测受影响 runner |

独立基准脚本完成后，用本轮含进度反馈的隔离产品再次验证脚本：线程池 4/16 中位数为 2,999/2,928 ms，差距约 2.4%。收益幅度会变动，不能仅挑选第一组较好的结果作为默认调参依据。

重编译本轮原生宿主后，独立冷运行时缓存验收记录：约 3.3 秒提交缓存，6.5 秒原生工作区就绪；加载截图已看到 `Unpacking runtime files... 17%`。原生启动、边缘命中和退出检查通过。该宿主的 WebView2 状态和 Portable 数据已存在，不是全新电脑验收，也不能与 Windows 2022 的 73 秒直接相减声称提速。源码测试 622 通过。

重复内容统计约 1,302 个文件、2 MB，主要包括许可证和小型模块；直接删除会破坏路径或许可完整性，硬链接又引入共享修改问题，本轮不采用这种去重。

## 慢启动尚未解决的部分

Windows 2022 原失败运行中，目录创建约 38 秒、文件展开约 22 秒。现有证据不足以把延迟归因于某个扫描器或磁盘因素。本轮改善了用户可见反馈与阶段测量，**不宣称已消除该冷启动瓶颈**。

同一份 `4907561` 成品的后续定向运行 `34687922128` 在 Windows 2022 上通过：目录阶段约 9 秒、缓存约 21 秒提交、原生工作区约 30 秒就绪。产品未改变，但 runner 实例不同；这证明环境波动影响显著，不证明特定扫描器是根因，也不能把两次差值归功于验收脚本修正。

定向工作流新增 `preparation` 范围，复用指定 CI 成品，分别在 Windows 2022/2025 上交替测量线程池 4/16；保存产品来源、胶囊哈希、Node 版本、分阶段耗时和全部样本。脚本不会改变系统设置、关闭扫描器或修改产品默认环境变量。该诊断不替代精确提交的成品资格验收。

下一步先根据受影响 runner 的测量决定参数是否值得调整；若仍主要受创建文件数量限制，再比较打包布局。任何延迟准备都必须证明被延迟的内容不被启动、插件、更新或离线恢复使用；不靠首次运行恰好没读到来判断文件可删。保留完整离线能力和内核可替换性，拒绝无证据的专用加载分支。

本地证据：`build/first-start-20260912/`；独立基准入口：`scripts/benchmark-runtime-preparation.mjs`。
